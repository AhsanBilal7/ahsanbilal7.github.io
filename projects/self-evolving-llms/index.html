Game-Theoretic Self-Evolution of Large Language Models

A Designer writes tasks and a Solver learns from them with a verifiable reward. Instead of a hand-tuned difficulty target, a minimax-regret game over the whole population of past models decides what the Solver should learn next.

  • Self-play & self-improvement
  • RL with verifiable rewards (GRPO)
  • Minimax regret · Nash equilibria
  • PSRO meta-games
  • Curriculum & data selection
  • Agentic software engineering

The problem

Self-play methods for LLMs reward the task writer with a difficulty heuristic (e.g. “aim for 50% success”). Difficulty says nothing about which weakness a task exposes, and the curriculum has no clear goal to converge to.

The idea

Turn curriculum design into a game. A task is valuable when the current model is far below what some model in the population already achieved on it. The game’s Nash equilibrium becomes the training mix.

The test

A controlled study on agentic software engineering: only the training-data selection changes; the model, data, verifier and compute stay fixed. The trained agent is judged end-to-end on real GitHub issues of SWE-bench Verified.

Research question Can an LLM find the environments that expose its own weaknesses, improve on them, and become robust across task families — with no hand-designed difficulty reward?

Key Idea

Difficulty is not a capability gap

Consider two tasks. A difficulty score prefers the one where the model is near 50%. But the more useful task is the one where the model is below what it (or another model) has already shown is possible — a gap that is real, measurable and learnable.

regret of a model on a task  =  best value any model in the population reached  −  value of this model

1

Population regret

The reference is not a fixed “perfect score” but the best result of a population: all past checkpoints plus frozen specialist models. Estimates are cross-fitted so a lucky run does not inflate the target.

2

A meta-game over the archive

Following PSRO, environments are rows and every archived checkpoint is a column. Because old checkpoints stay in the game, a skill that the newest model forgot shows up as regret.

3

Nash curriculum

A small linear program solves the zero-sum game. The designer’s equilibrium strategy is the training mix; a small exploration share keeps unsolved “frontier” tasks in play.

Part 1 · Method

Two-policy self-evolution with a minimax-regret game

One pretrained model is cloned into a Designer and a Solver. From then on they have separate weights, optimizers and checkpoints, and each is updated against a frozen opponent — so the reward reference does not move during an update. One iteration of the loop:

What this fixes in current self-play methods

Each design choice answers a concrete failure mode in recent LLM self-play work (R-Zero, Absolute Zero, SPADE, EvoEnv, …).

Limitation 1Difficulty is not a capability gap
Population regret rewards only gaps that some policy has already closed.
Limitation 2Self-referential “regret” is difficulty in disguise
The reference comes from other, frozen policies; the solver cannot shrink its regret by collapsing its output diversity.
Limitation 3The optimal value of a task is unknown
Best value of archived checkpoints and specialist antagonists, cross-fitted, with a confidence bound against noise.
Limitation 4Latest-only self-play cycles and forgets
A PSRO meta-game over the full archive; an old checkpoint that still solves a task keeps its regret visible.
Limitation 5The designer can hack its reward
A validity gate, novelty and invalidity penalties, and a verifier the designer cannot change.
Limitation 6Success is measured by the method’s own reward
Absolute, held-out metrics on one final model: worst family, tail (CVaR) and mean, at equal compute.
Limitation 7One shared policy couples both roles
Two independent policies, separate optimizers, and a frozen opponent in every update.
In one lineOne game replaces the hand-made heuristics

Task value, curriculum, anti-forgetting and the Designer’s reward all come from the same population-regret meta-game.

Part 2 · Empirical testbed

Which training turns should a coding agent learn from?

Before training a Designer, I isolate the core question on a real agent-training setup. PivotRL trains an agent on single decision points (“pivots”) of expert coding-agent trajectories, and picks them by difficulty. Here the pool of candidate pivots is fixed, and the regret game acts as the selector: can population regret and its Nash equilibrium choose more useful training turns than a difficulty filter?

Training signal

Each pivot is one tool call of a coding agent (edit, search, run a command, …). A fixed functional verifier gives reward 1 only if the call does the right thing on the right target.

Families = repositories

Pivots are grouped by source repository: each has its own code base, tests and tools. Selection happens at family level, which keeps the game’s estimates stable.

Clean splits

Splits are made by issue, never by turn, and training issues are audited against the benchmark: zero overlap; no benchmark repository is used for training.

End-to-end task success

The trained model runs as a full OpenHands agent on the 500 real issues of SWE-bench Verified; the official harness runs the issue’s tests. Resolve rate, plus the worst repository.

Robustness across families

Held-out decision accuracy on unseen issues: mean, worst family, CVaR0.2 (the weakest 20% of families) and the families that were weakest at the start.

Forgetting

Every checkpoint is profiled, so I can see if a family that was learned earlier is lost later.

Equal compute, real uncertainty

Same number of training rollouts for all methods; selection cost is reported on top. Multiple seeds, confidence intervals and paired comparisons against the baselines.

Status & Roadmap

Where the project is

  1. Stage 1 · Simulation done

    CPU simulation of the game and the estimators, to check that the selectors behave as designed.

  2. First testbed on tool-use conversations done

    Showed that a plain Nash selector can lock onto one family; this led to the soft-Nash variant.

  3. SWE data, decontamination & pipeline done

    Repository families, issue-level splits, zero overlap with the benchmark, end-to-end smoke test.

  4. Stage 2 · Fixed-pool SWE experiment running

    5 selection methods × 3 seeds on an open small model, then SWE-bench Verified for every final checkpoint.

  5. Stage 3 · Full two-policy game next

    A trainable Designer that writes executable environments, with the Nash curriculum for the Solver, at 1.7B and 4B scale.

Open problem 1 · zero-regret frontier

If no model solves a valid task, its regret is zero and the equilibrium ignores it — yet it may hold a new skill. Fix: a small exploration budget on “frontier” tasks and a specialist that tries to unlock them, so they can enter the game.

Open problem 2 · designer writes the verifier

A designer could write a checker that accepts a shortcut. Fix: audit a random subset against trusted reference implementations, kept outside the designer’s reward, and report the disagreement rate as a reward-hacking metric.

Questions I often get

Q&A

Why not simply target tasks with ~50% success?

Because difficulty measures uncertainty, not a learnable weakness. A 50% task may be at the ceiling of every model, while a 20% task that an earlier checkpoint solved at 90% is a gap we know can be closed. Regret against a population captures the second kind.

Why a Nash equilibrium instead of “always train the weakest family”?

Greedy worst-first chases noise and oscillates, and it only looks at the newest model. The equilibrium is computed over all archived checkpoints, so it hedges across several weaknesses at once and keeps forgotten skills visible. In non-transitive cases (checkpoint A knows arithmetic, B knows logic) it trains on both and stops the cycle.

Where does the “best possible” value come from?

From the population: every archived checkpoint plus frozen specialist models. Taking the maximum of noisy estimates is biased upward, so the selection and the measurement use different halves of the data (cross-fitting), and the designer reward uses a lower confidence bound.

How do you stop the Designer from gaming its reward?

Only certified environments count: they must be deterministic, solvable by their reference solver, reject wrong and trivial answers, run within limits, and not be trivial for the base model. Near-copies and invalid tasks are penalised, the evaluation verifier is fixed, and a trusted subset is audited.

Why two separate models instead of one shared model?

With shared weights, one gradient step moves both the task writer and the task solver, so the reference for the reward changes during the update. Separate policies with frozen opponents make each update a well-defined best response — the PSRO view.

Does a robust mixture of checkpoints mean a robust single model?

Not automatically. The equilibrium is a mixture of archived solvers. That is why every result is reported for the single final checkpoint, and the mixture is only a diagnostic.

Why software engineering as the testbed?

It is a real agentic setting with natural families (repositories), cheap verifiable rewards for single decisions, and a hard, trusted end-to-end benchmark (SWE-bench Verified) that is fully separate from training.
